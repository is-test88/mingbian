# 《明辨录》交付模板

这是一套可裁剪的结构，不是必填表。只展示有内容的部分；不把未知用看似合理的数字或姓名补齐。简单事项用几段文字即可。

```markdown
# 明辨录｜主题

## 本次结论
方向就绪／试点就绪／执行就绪／尚未就绪。
适用范围；当前建议；不能据此推导的其他承诺。

## 目标与路径
要改变的结果、对象、成功证据、不做什么。
为什么当前路径能够导致该结果；关键选择及理由。

## 已定与边界
已经明确确认的决策及适用条件。
范围、资源、时间、权限与风险边界。
建议责任角色与已确认负责人分别标明。

## 落地与验收
按实际需要写关键步骤，而非空泛“建立机制、加强协同”。
触发 → 输入／规则 → 动作 → 输出／回读 → 责任／交接 → 验收。
重大异常的接管、暂停或回退；验收角色与完成证据。

## 依据与未尽
已核实事实与来源；用户陈述；透明默认与撤回方式。
假设 → 验证办法 → 触发 → 责任及确认状态 → 通过条件／失败动作。
后议 → 触发 → 谁判断 → 判断依据 → 临时处理。
阻断 → 影响哪些动作 → 解锁条件 → 可先开展什么。

## 下一步
最先可安全开展的动作；责任角色及确认状态；完成证据。
```

## 三种深度

**方向就绪**：对路径选择已有足够依据，知道下一步应验证什么。可以省略生产操作细则，不能省略当前决策的关键假设和边界。

**试点就绪**：除了方向，试点的范围、投入边界、负责人、方法、验收与停止条件已明确。全面推广仍需要验证结果，不提前承诺。

**执行就绪**：关键路径可交接，重大例外可接管，结果可验收；后议不能阻断本阶段动作。

**尚未就绪**：仍有关键阻断，或用户提前收尾。保留所有已形成内容，说明缺什么、为什么影响当前行动，给出安全的下一步。并非必须继续发问。

## 交付前自检

是否把用户倾向写成了决策？是否把建议角色写成了已指派的人？是否用了未经确认的时间、金额或指标？是否把原文“用户陈述”变成“系统已核实”？是否只证明做过，没定义做成？是否在结尾额外加了不必要的确认问题？

若答案为是，先改产物，再交付。结构完整不能替代内容可信。
