# 明辨簿｜会话状态协议

## 一、何时开簿

“明辨簿”用于跨会话恢复、复杂依赖、多人协同和审计留痕，不是普通明辨对话的默认步骤。

满足以下任一条件时再使用：

- 用户明确要求暂停后继续、跨天恢复或多人接力；
- 当前关键未决分支超过 5 个，且存在明显硬依赖；
- 方案需要经历多个阶段或较长周期；
- 需要保留事实证据、决策变化、失效原因和授权边界；
- 用户明确要求可审计、可回放的推演记录。

单次对话内的少量事项，维护轻量台账即可。不要为了开簿而把方案拆成过多节点。

## 二、簿中记什么

CLI 内部使用 `tree`、`branch`、`decision`、`fact` 等稳定字段；概念上记录的是一张最小**辨题图**。

输入可为数组，或包含 `branches` 数组的对象：

```json
{
  "branches": [
    {
      "id": "D01",
      "kind": "decision",
      "title": "首期所求之成",
      "question": "首期只需证明端到端跑通，还是必须同时证明效率收益？",
      "recommendation": "先以端到端跑通、质量护栏和结果回读作为首期验收。",
      "rationale": "不同答案会改变首期范围、数据要求、排期与验收。",
      "parent_id": null,
      "depends_on": [],
      "priority": 10
    },
    {
      "id": "F01",
      "kind": "fact",
      "title": "当前流程耗时基线",
      "question": "查实当前端到端流程的人工作业时长。",
      "recommendation": "读取近四周流程日志并抽样复核。",
      "rationale": "若首期要证明效率收益，该事实将决定基线与样本要求。",
      "parent_id": "D01",
      "depends_on": [],
      "priority": 20
    }
  ]
}
```

字段含义：

- `kind`：只能是 `decision` 或 `fact`；
- `question`：对 `decision` 是需要责任人承担的单一取舍；对 `fact` 是代理需要查实的明确命题；
- `recommendation`：对 `decision` 是明确判断；对 `fact` 是建议查实方式；
- `rationale`：必须说明它会改变哪一层：本、路、界、序、法或成；
- `priority`：整数越小越优先；
- `parent_id` 与 `depends_on`：均为硬前置，不用于普通主题分组。

只记尚未解决、且会影响结果或执行一致性的分支。不要把完整方案逐句拆入簿中。

## 三、方向锁定后，如何展开细节

辨题图应渐进展开：

1. 初始优先记录辨本、辨路和主要边界；
2. 上游结论锁定后，再新增被其解锁的辨序、辨法与辨成分支；
3. 只有会造成执行分歧、风险、返工或验收不一的细节才入簿；
4. 可逆、低风险、有明显优选的细节以透明默认记录在最终《明辨录》中，不必全部入图；
5. 后议事项必须有触发时点、责任人和判断依据；否则仍是未解决分支。

不得为了“树完整”预先穷举所有实现细节，也不得因初始图只有上游问题，就在方向锁定后忘记下沉。

## 四、显式假设如何记

脚本不单设 `assumption` 类型，避免把事实、风险接受和验证计划混为一谈：

- 若必须拿到证据才能继续：保留为 `fact`，查不到且风险不可接受时 `block`；
- 若可在护栏下继续：写成 `decision`，让责任人决定是否接受该假设，并写明验证时点、失败触发和责任人；
- 最终输出时归入《明辨录》的“显式假设及验证方式”，不得写成已核实事实。

示例：

```json
{
  "id": "D02",
  "kind": "decision",
  "title": "样本量假设",
  "question": "首期是否接受日均任务量不少于 50 的工作假设，并在上线首周验证？",
  "recommendation": "可以接受，但低于 30 时应重新评估投入产出。",
  "rationale": "当前无法取得完整历史数据，但该不确定性可以低成本验证，不必阻断试点。",
  "parent_id": null,
  "depends_on": [],
  "priority": 30
}
```

## 五、如何改簿

`apply` 读取一个 `operations` 数组并原子执行；任一操作失败，整批不写入。

```json
{
  "operations": [
    {
      "op": "lock",
      "id": "D01",
      "answer": "首期只验证端到端跑通，并设置质量与回读护栏"
    },
    {
      "op": "add",
      "branch": {
        "id": "D03",
        "kind": "decision",
        "title": "异常接管边界",
        "question": "哪些异常必须停止自动执行并转人工？",
        "recommendation": "任何可能造成错误业务写入、权限越界或不可逆损失的异常均转人工。",
        "rationale": "该边界决定首期能否安全运行，以及人工接管量。",
        "parent_id": "D01",
        "depends_on": [],
        "priority": 15
      }
    }
  ]
}
```

支持操作：

- `lock`：锁定决策答案或事实结论；事实必须附非空 `evidence`；
- `add`：新增被当前答案解锁的关键分支；
- `revise`：修改问题、判断、理由、依赖或优先级，必须说明 `reason`；
- `invalidate`：标记已不再适用，必须说明原因；
- `block`：记录止步原因与缺失条件；
- `reopen`：因新信息重开旧结论，必须说明原因。

## 六、动态改簿规则

- 锁定分支前，其全部硬前置必须已锁定；
- 新答案推翻旧结论时，先 `reopen` 受影响分支，再原子处理下游；
- 前置分支失效后，下游开放项会成为 `orphaned`，必须失效或重新挂接；
- 不相关的待查事实不得阻塞独立决策；
- 方向分支锁定后，应主动检查是否需要新增关键落地分支；
- 不机械沿用最初的问题清单，每次作答后都要重算；
- 用户的偏好、正式决策与执行授权必须分别记录在自然语言答案中，不擅自扩大含义。

## 七、状态如何读

`status` 返回：

- `plan_source`：绑定的方案来源；文件来源带初始化时 SHA-256；
- `locked_decisions`：已定之策；
- `verified_facts`：已明之实及证据；
- `invalidated`：已失效分支及原因；
- `facts_to_resolve`：当前可由代理查实的事实；
- `ask_now`：当前可请用户决断的辨题；顺序模式最多 1 个，frontier 模式最多为 `max_frontier`；
- `additional_frontier_decisions`：已解锁但本轮未展示的独立决策；
- `waiting`：仍待前置条件的开放项；
- `orphaned`：因前置失效而需重挂或失效的开放项；
- `blocked`：止步项；
- `can_confirm`：当前辨题图是否已无未解决分支。

`can_confirm=true` 只表示图中事项已处理，不自动证明《明辨录》已经覆盖全部关键落法。确认前仍需按六层与陌生执行者检验做一次整体复核。

## 八、确认与关闭

`confirm` 只在 `can_confirm=true` 时成功。关闭代表“本次《明辨录》已确认”，不自动代表外部写入、发布、删除、付款或发送消息已获授权。

当前明辨簿协议使用 `schema_version: 2`。会话文件必须明确携带该字段；协议版本不匹配时应停止写入，并先完成结构核验或显式迁移。

## 九、存储与安全

主命令：

```bash
python3 scripts/mingbian_session.py ...
```

默认目录：

```text
~/.mingbian_sessions
```

环境变量：

```text
MINGBIAN_SESSIONS_DIR
```

可通过全局 `--store-dir` 显式指定其他目录。新建目录权限为 `0700`，会话文件为 `0600`；更新使用同目录临时文件与原子替换，避免半写入状态。

不要把口令、令牌、完整个人敏感信息写入分支、答案或证据。只保留支持明辨所需的最少内容。
